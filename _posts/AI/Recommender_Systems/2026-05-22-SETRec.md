**Order-agnostic Identifier for Large Language Model-based Generative Recommendation**  
(Xinyu Lin, Haihan Shi, Wenjie Wang, Fuli Feng, Qifan Wang, See-Kiong Ng, Tat-Seng Chua, SIGIR 2025)

## 1. 연구 배경

### 1. LLM 기반 생성형 추천

LLM 기반 생성형 추천에서는 사용자의 과거 상호작용 정보를 입력으로 넣고, <br> LLM이 다음에 추천할 item identifier를 생성하도록 학습 <br><br>

여기서 **item identifier**란, <br>
각 item을 LLM이 입력으로 읽고, 출력으로 생성할 수 있도록 바꾼 토큰 표현을 의미한다.<br><br>

사용자 history를 다음과 같이 표현했을 때, <br>

$S_u = [i_1^u, i_2^u, ... , i_L^u]$

<br>
각 item은 tokenizer f(.)를 통해 LLM이 처리할 수 있는 형태로 변환된다.<br><br>

$x = [f(i_1), f(i_2), ... , f(i_L)]$

이후 LLM recommender M(.)는 입력 x를 encoding한 뒤, 다음 item identifier를 생성한다.<br><br>

즉, 생성형 추천의 핵심은 <span style="background-color: #fff3cd">item을 어떻게 identifier로 표현할 것인가</span>에 있다.

---

### 2. 기존 방식 1: Token-sequence Identifier

첫 번째 기존 방식은 **Token-sequence Identifier**이다. <br><br>

Token-sequence identifier는 item의 semantic 정보나 CF 정보를 여러 개의 이산적인 토큰 시퀀스로 표현한다. <br>

예를 들어 하나의 item identifier는 다음과 같이 표현될 수 있다.<br>

$\tilde{i} = [z_1, z_2, \ldots, z_N]$

이 방식의 **장점**은 item 정보를 비교적 풍부하게 표현할 수 있다는 점이다.  <br>
하나의 embedding에 모든 정보를 압축하는 것이 아니라 여러 token으로 나누어 표현하기 때문에, semantic 정보나 collaborative filtering 정보를 더 자세히 담을 수 있다.<br><br>

하지만 **단점**도 존재한다.<br>
Token-sequence identifier는 autoregressive 방식으로 token을 하나씩 순차 생성해야 한다.  <br>
따라서 다음 token을 생성할 때마다 LLM call이 필요하고, 이로 인해 추론 속도가 느려진다.<br><br>

또한 beam search를 사용할 경우 **local optimum 문제**가 발생할 수 있다.<br>

Beam search는 각 step에서 확률이 높은 token sequence만 유지한다.  <br>
따라서 초기에 정답 token의 확률이 낮으면, 실제로는 좋은 정답 sequence였더라도 중간 단계에서 pruning될 수 있다.<br>

<span style="color: blue">즉, token-sequence 방식은 item 정보를 풍부하게 표현할 수 있지만, 순차 생성으로 인해 추론 효율성이 떨어지고 beam search 과정에서 정답 sequence가 제거될 위험이 있다.</span> <br><br>

![Figure 1. Token-sequence identifier와 beam search 문제](/assets/images/SETRec_Figure_1.png)

### 3. 기존 방식 2: Single-token Identifier

두 번째 기존 방식은 **Single-token Identifier**이다. <br>

Single-token identifier는 각 item을 하나의 embedding으로 표현한다.<br><br>

$\tilde{i} = z$

이 방식은 token-by-token 생성이 필요하지 않기 때문에 빠른 추론이 가능하다. (token by token, autoregressive 생성 X) <br> <br>

하지만 하나의 embedding만으로 item의 semantic 정보와 CF 정보를 모두 담기 어렵다는 한계가 있다.<br>

예를 들어 어떤 item이 가진 의미 정보, category 정보, 사용자의 상호작용 패턴 기반 정보 등을 하나의 vector에 모두 압축하면 embedding collapse나 정보 손실이 발생할 수 있다.<br>

따라서 single-token identifier는 효율성 측면에서는 유리하지만, item 정보를 충분히 표현하기에는 한계가 있다.

---

### 4. SETRec의 제안 방향

SETRec은 기존 두 방식의 장점을 결합하기 위해 item을 **order-agnostic token set**으로 표현한다.<br><br>

<span style="background-color: #fff3cd">item = {CF token, semantic tokens}</span>

<br><br>
하나의 item을 CF token과 여러 semantic token으로 구성된 set identifier로 표현한다.<br>

이 방식은 장점은 다음과 같다. <br>

1. CF 정보와 semantic 정보를 함께 활용할 수 있다.<br>
2. token 간 순서 의존성을 제거할 수 있다.<br>
3. token을 동시에 생성하여 빠른 inference가 가능하다.<br><br>

따라서 SETRec은 token-sequence 방식의 풍부한 표현력과 single-token 방식의 빠른 추론 속도를 동시에 얻고자 한다.

## 2. SETRec

### 1. 전체 프레임워크

SETRec의 전체 구조는 크게 세 단계로 나눌 수 있다.<br><br>

1. **Order-agnostic Item Tokenization**
2. **Simultaneous Item Generation**
3. **Item Grounding**

<br><br>
먼저 각 item은 CF token과 semantic tokens로 변환된다.  <br>
이후 사용자의 historical interactions는 item token set의 sequence로 표현된다.  <br>
마지막으로 query vector를 활용해 다음 item의 token들을 동시에 생성하고, 생성된 token set을 실제 item으로 grounding한다.<br><br>

![Figure 3. SETRec Framework](/assets/images/SETRec_Figure_3.png)

---

### 2. Order-agnostic Item Tokenization

SETRec은 하나의 item을 순서가 없는 token set으로 표현한다. <br>

예를 들어 basketball hoop item은 다음과 같이 표현될 수 있다.<br>

${CF, basketball, toy sports, mini hoop}$

<br>
여기서 CF token은 collaborative filtering 정보를 담고, semantic tokens는 item의 의미 정보를 담는다.

---

#### CF Tokenizer

CF Tokenizer는 pretrained CF model을 이용하여 사용자의 상호작용 패턴을 기반으로 item의 collaborative information을 담은 CF embedding을 생성한다.<br>

논문에서는 pretrained CF model로 SASRec을 사용한다.<br>

$z_{CF} \in \mathbb{R}^d$
<br><br>

---

#### Semantic Tokenizer

Semantic Tokenizer는 item의 semantic 정보를 여러 개의 semantic token으로 분리한다. <br> <br>

먼저 item의 description, category 등의 정보를 사전학습된 semantic extractor인 SentenceT5로 embedding하여 semantic representation s를 생성한다.<br>

이후 s를 encoder에 넣어 N개의 order-agnostic semantic token으로 분리한다.<br><br>

$z = [z_{S1}, z_{S2}, ... , z_{SN}]$

이렇게 여러 개의 semantic token으로 나누는 이유는 하나의 embedding에 모든 semantic 정보를 압축할 때 발생할 수 있는 **embedding collapse**와 정보 손실을 완화하기 위해서이다. <br><br>

또한 semantic tokens가 원래 semantic representation의 의미 정보를 유지하도록 auto-encoder 방식의 reconstruction loss를 사용한다.<br><br>

$\mathcal{L}_{AE} = \|s - \hat{s}\|_2^2$

즉, decoder가 semantic tokens로부터 원래의 semantic representation $s$를 복원하도록 학습한다.<br>

---

#### Token Corpus

SETRec은 모든 item token을 dimension별 token corpus로 저장한다.<br><br>

이 token corpus는 이후 generated token set을 실제 item으로 grounding할 때 사용된다.<br>

모델이 생성한 token 조합이 실제 item과 정확히 대응되지 않을 수 있기 때문에, token corpus를 grounding head로 활용하여 실제 item score를 계산하고 ranking을 수행한다.<br><br>

<span style="background-color: #fff3cd">정리하면, SETRec의 item identifier는 CF token과 semantic tokens로 구성된 order-agnostic token set이다.</span>

![Figure 4. Order-agnostic Item Tokenization](/assets/images/SETRec_Figure_4.png)

---

### 3. Simultaneous Item Generation

기존 token-sequence 방식은 token을 순차적으로 생성했었다.  <br>
반면 SETRec은 CF token과 semantic tokens를 동시에 생성한다.<br>

이를 위해 SETRec은 **Query-guided Generation**을 사용한다.<br><br>

각 정보 dimension마다 learnable query vector를 두고, 각각의 query vector가 해당 dimension의 token을 생성하도록 한다.<br>

예를 들어 다음과 같은 query vector들이 존재할 수 있다.<br><br>

$q_{CF}, q_{S1}, q_{S2}, ... , q_{SN}$

<br><br>각 query vector는 다음 item의 CF token 또는 semantic token을 생성한다.<br>

사용자 history가 다음과 같이 주어졌다고 하자.<br>

$x = [\{z_{CF}, z_{S1}, ... , z_{SN}\}^1, ... , \{z_{CF}, z_{S1}, ... , z_{SN}\}^L]$

<br><br>이때 SETRec은 LLM layers를 통과한 뒤 다음 item의 token set을 동시에 생성한다.<br>

$\hat{z} = [\hat{z}_{CF}, \hat{z}_{S1}, ... , \hat{z}_{SN}]$

<br><br>즉, token-by-token 생성이 아니라 모든 token을 한 번에 생성한다.<br>

---

#### Token Generation Optimization

Token generation optimization의 목표는 generated token이 target item token과 가까워지고, 같은 dimension에 있는 다른 token과는 멀어지도록 학습하는 것이다.<br>

이를 위해 contrastive learning 형태의 loss를 사용한다.<br>

$\mathcal{L}_{Gen} = \frac{1}{D}\sum_i -\log \frac{\exp(\mathrm{sim}(\hat{z}_i, z_i^+))}{\sum_{z \in \mathcal{Z}_i}\exp(\mathrm{sim}(\hat{z}_i, z))}$

여기서 $\hat{z}_i$는 generated token, $z_i^+$는 target item의 정답 token, $\mathcal{Z}_i$는 같은 dimension에 속한 token corpus를 의미한다.<br><br>

<span style="background-color: #fff3cd">즉, 정답 token과의 similarity는 높이고, 같은 dimension의 다른 token들과의 similarity는 낮추도록 학습한다.</span>

---

#### Token Grounding

동시에 생성된 token 조합이 반드시 실제 item에 해당한다고 보장할 수는 없다.<br>

따라서 SETRec은 token corpus를 grounding head로 사용하여 실제 item score를 계산한다.<br>

최종 score는 CF score와 semantic score를 결합하여 계산한다.<br>

$s = (1-\beta)s_{CF} + \beta \sum_{k \in \mathcal{F} \setminus \{CF\}} s_k$

<br><br>
여기서 $\beta$는 semantic score의 비중을 조절하는 hyper-parameter이다.<br>

$\beta = 0$이면 CF score만 사용하고, $\beta = 1$이면 semantic score만 사용한다.<br>

<span style="color: blue">즉, SETRec은 generated token set을 그대로 추천 결과로 사용하는 것이 아니라, 실제 item corpus와 비교하여 valid item으로 grounding한다.</span><br>

---

### 4. Sparse Attention Mask

SETRec은 item을 order-agnostic token set으로 표현하지만, 실제로 LLM에 입력할 때는 token들을 한 줄로 나열해야 한다. <br>

이 과정에서 순서가 없는 token set임에도 불구하고, LLM에 sequence 형태로 입력되면 item 내부 token 사이에 불필요한 순서 의존성이 생길 수 있다는 문제가 생긴다. <br>

예를 들어 하나의 item이 다음과 같이 표현된다고 하자.<br>

$Item_1 = \{CF_1, S_{11}, S_{12}\}$

이 token들은 순서가 없는 set이어야 하지만, sequence로 입력되면 앞 token과 뒤 token 사이에 attention 관계가 생길 수 있다.<br><br>

이를 해결하기 위해 SETRec은 **Sparse Attention Mask**를 사용한다.<br>

Sparse Attention Mask의 핵심은 다음과 같다.<br>

1. 같은 item 내부 token끼리는 attention을 차단한다.<br>
2. 이전 item의 token들은 참조할 수 있다.<br>

<span style="background-color: #fff3cd">즉, 같은 item 안의 CF token과 semantic token은 서로 독립적으로 처리되지만, 과거에 interaction한 이전 item들의 정보는 활용할 수 있게된다.</span>
<br> <br>
기존 attention mask의 time complexity는 다음과 같았다. -> $O(M^3L^2d)$<br><br>

Sparse attention mask를 적용하면 다음과 같이 감소한다. -> $O(M^2L^2d)$ <br><br>

여기서 각 기호의 의미는 다음과 같다.<br>

- $M$: 정보 dimension 개수, 즉 CF token과 semantic token의 개수
- $L$: 사용자의 과거 interaction item 개수
- $d$: LLM hidden embedding dimension 크기

정리하면, <span style="background-color: #fff3cd">Sparse Attention Mask는 item 내부 token 간 순서 의존성을 줄이고, 동시에 계산 효율성도 개선한다.</span><br>

![Figure 5. Original Attention Mask와 Sparse Attention Mask](/assets/images/SETRec_Figure_5_sparse_attention_mask.png)

---

### 5. 학습 및 추론 과정

SETRec의 전체 학습 및 추론 과정은 다음과 같이 정리할 수 있다. <br>

1. 모든 item을 set identifier로 tokenization한다.<br>
2. dimension별 token corpus Z를 생성한다.<br>
3. user history를 identifier sequence로 변환한다.<br>
4. query-guided generation과 sparse attention mask를 사용하여 token을 동시에 생성한다.<br>
5. token corpus를 grounding head로 사용한다.
6. generated token set을 valid item으로 grounding한다.<br>

전체 학습 loss는 다음과 같이 구성된다.<br>

$\mathcal{L} = \mathcal{L}_{Gen} + \alpha \mathcal{L}_{AE}$

<br>
여기서 $L_{Gen}$은 token generation loss이고, $L_{AE}$는 semantic token이 원래 semantic representation을 복원하도록 하는 auto-encoder loss이다.<br>

$\alpha$는 AE loss의 strength를 조절하는 hyper-parameter이다.<br>

## 3. 실험

### 1. RQ1: Overall Performance

첫 번째 실험의 목적은 SETRec이 기존 방법들보다 전체적으로 우수한 추천 성능을 보이는지 확인하는 것이다.
<br>

#### 실험 설정

**dataset**<br>

- Amazon Toys
- Amazon Beauty
- Amazon Sports
- Steam

각 dataset은 warm item과 cold item으로 분리하여 평가 <br> 
train, valid, test = 8:1:1<br>

평가지표 =  Recall@K, NDCG@K<br> (K = 5, 10)<br>

모델: T5와 Qwen-1.5B를 사용<br>

실험은 NVIDIA RTX A5000 GPU 환경에서 수행<br>

---

#### Baselines

비교한 baseline은 아래와 같다. <br>

- E4SRec

Token-sequence 방식: <br>
- BIGRec
- IDGenRec
- CID
- SemID
- TIGER
- LETTER

#### Overall Performance on T5

T5 기반 실험 결과 <br>

1. Token-sequence identifier가 single-token identifier보다 전반적으로 우수했다.
2. Token-sequence 방식 중에서는 external token 기반 방법이 all/warm setting에서 더 강했다.
3. Cold item 추천에서는 semantic 정보를 활용하는 방법이 유리했다.
4. SETRec은 모든 설정에서 가장 우수한 성능을 보였다.
5. SETRec은 추천 성능뿐 아니라 추론 효율성도 개선하였다.

> 즉, SETRec은 semantic 정보와 CF 정보를 함께 활용하면서도 token-by-token 생성 문제를 줄였기 때문에 성능과 효율성을 모두 개선할 수 있었다.

### 2. RQ2: Ablation Study

SETRec의 각 구성 요소가 실제로 성능에 얼마나 기여하는지 분석하기 위한 ablation study <br>

---

#### Motivation

SETRec은 CF token, semantic token, learnable query vector, sparse attention mask 등 여러 구성 요소로 이루어져 있다.<br>

따라서 각 요소를 제거했을 때 성능이 어떻게 변하는지 확인함으로써, 각 구성 요소의 효과를 검증한다.<br><br>

---

#### Setting

T5와 Qwen-1.5B에서 Toys dataset을 사용하였다.<br>

비교한 ablation variant는 다음과 같다.<br>

- w/o Sem: semantic token 제거
- w/o CF: CF token 제거
- w/o Query: 학습 가능한 query vector를 랜덤 고정된 벡터로 대체
- w/o SA: sparse attention mask 대신 기존 attention mask 사용

---

#### Result
1. Warm, Cold 모두에서 어떤 구성 요소를 제거해도 성능이 하락했다.<br>
2. Semantic token을 제거하면 cold item 성능이 크게 하락했다.<br>
3. Semantic token 제거의 영향이 CF token 제거보다 더 컸다.<br><br>

이를 통해 SETRec에서 semantic token이 특히 중요하다는 점을 확인할 수 있다.<br>

특히 cold item의 경우 과거 interaction 정보가 부족하기 때문에 CF 정보만으로는 충분한 추천이 어렵다.  <br>
따라서 item의 description, category 등에서 얻은 semantic 정보가 cold item 추천 성능 개선에 크게 기여한다.<br>

### 3. RQ3: Item Group Analysis

본 실험은 SETRec이 인기 item뿐 아니라 long-tail item에서도 강한 성능을 보이는지 확인하기 위한 실험이다.<br>

---

#### Motivation

추천 시스템에서는 popular item에 대한 추천은 상대적으로 쉽지만, interaction이 적은 long-tail item에 대한 추천은 어렵다.<br><br>

따라서 SETRec이 sparse하거나 unpopular한 item에서도 강한 성능을 보이는지 확인할 필요가 있다.<br>

---

#### Setting

Toys dataset을 사용하고, item popularity를 기준으로 item을 G1부터 G4까지 나누었다.<br>

- G1: most popular
- G4: least popular

비교 모델은 SETRec, LETTER, E4SRec이다.<br>

---

#### Result

1. 인기도가 낮아질수록 전체 성능은 감소했다.<br>
2. 하지만 SETRec은 모든 그룹에서 가장 우수한 성능을 보였다.<br>
3. 특히 sparse하고 unpopular한 item에서 강한 성능을 보였다.<br>

이는 SETRec이 단순히 인기 item 추천에만 강한 것이 아니라, long-tail item 추천에서도 효과적임을 보여준다.<br>

#### Motivation

### 5. RQ4: Effect of Semantic Strength $\beta$

이 실험은 inference 단계에서 semantic score의 비중이 성능에 어떤 영향을 주는지 확인하기 위한 실험이다.<br>

---

#### Motivation

SETRec은 최종 item score를 계산할 때 CF score와 semantic score를 함께 사용한다.<br>

$s = (1-\beta)s_{CF} + \beta \sum_{k \in \mathcal{F} \setminus \{CF\}} s_k$

여기서 $\beta$는 semantic score의 비중을 조절하는 hyper-parameter이다.<br>

따라서 $\beta$ 값을 변화시키면서 semantic 정보가 추천 성능에 미치는 영향을 분석한다.<br>

---

#### Setting

$\beta$ 값을 0부터 1까지 변화시키며 실험하였다.<br>

- $\beta = 0$: CF score만 사용
- $\beta = 1$: semantic score만 사용

Warm setting과 Cold setting에서 각각 비교하였다.<br>

---

#### Result

1. $\beta > 0$일 때 성능이 향상되었다.<br>
2. Semantic 정보는 특히 cold item 성능 개선에 중요했다.<br>
3. CF 정보와 semantic 정보를 함께 조합하는 것이 가장 안정적이었다. <br>

CF 정보만 사용하는 것보다 semantic 정보를 함께 사용하는 것이 더 좋은 성능을 보이며, <br>
특히 cold item 추천에서 semantic 정보의 효과가 크게 나타난다.<br>

![Figure 8. Effect of Semantic Strength Beta](/assets/images/SETRec_Figure_8.png)

### 6. RQ4: Hyper-parameter Sensitivity

마지막 실험은 AE loss strength $\alpha$와 semantic token 수 N이 성능에 미치는 영향을 분석하기 위한 실험이다. <br>

---

#### Motivation

SETRec은 semantic token을 학습할 때 auto-encoder reconstruction loss를 사용한다.  <br>
또한 semantic representation을 몇 개의 token으로 분리할 것인지도 중요한 hyper-parameter이다.<br>

따라서 $\alpha$와 N을 변화시키면서 성능 변화를 확인한다.<br>

---

#### Setting

Toys dataset을 사용하였고, <br>
변화시킨 hyper-parameter는 다음과 같다.<br>

- AE loss strength $\alpha$
- semantic token 수 $N$
<br>
All, Warm, Cold setting에서 성능을 비교하였다.

---

#### Result

1. $\alpha$는 0.5에서 0.7 범위에서 좋은 성능을 보였다.<br>
2. N이 증가하면 성능이 좋아지지만, 너무 많으면 성능이 저하될 수 있다.<br>
3. 적절한 semantic token 수와 AE 학습 강도 조절이 중요하다.<br>

semantic token을 너무 적게 사용하면 의미 정보를 충분히 표현하기 어렵고, <br>너무 많이 사용하면 오히려 불필요한 noise나 학습 부담이 증가할 수 있다.<br>

## 4. 결론 (내가 생각한)

### 1. 공헌

1) 새로운 **set identifier 패러다임**을 제안하였다. <br>

기존 방식은 item을 token sequence 또는 single token으로 표현했다.  <br>
반면 SETRec은 각 item을 semantic 정보와 CF 정보를 포함하는 order-agnostic token set으로 표현한다.<br><br>

2) **Sparse Attention Mask**를 통해 순서 불변성을 보장하였다.<br>

item 내부 token 간 attention을 차단함으로써, CF token과 semantic token이 불필요한 순서 의존성을 갖지 않도록 한다.  <br>
이를 통해 각 정보 dimension을 독립적으로 처리할 수 있다.<br><br>

3) **Query vector 기반 동시 생성 방법**을 제안하였다.<br>

CF token과 semantic token을 동시에 생성할 수 있도록 하여, token-by-token 생성 없이 빠른 추론이 가능하도록 만들었다.<br><br>

4) 다양한 실험을 통해 성능을 검증하였다. <br>

SETRec은 T5와 Qwen 1.5B부터 7B까지의 모델에 적용되었으며, 4개의 real-world dataset에서 effectiveness, efficiency, generalization ability, scalability를 검증하였다. <br>


---

### 2. 한계

1) 사용자 측 정보 모델링이 상대적으로 약하다.<br>

SETRec은 주로 item identifier 설계에 초점을 맞춘 논문이다.  <br>
따라서 user의 장기 취향, 단기 의도, context 변화 자체를 정교하게 모델링하는 부분은 상대적으로 약하다.<br>

향후 연구에서는 item identifier뿐 아니라 user representation을 더 정교하게 설계할 필요가 있다.

2) online evaluation이 부족하다.

논문은 offline dataset에서 Recall과 NDCG 중심으로 성능을 검증하였다.  
하지만 실제 추천 서비스에서는 사용자의 클릭, 체류 시간, 구매 전환, 피드백 변화 등이 중요하다.

따라서 실제 서비스 환경에서 SETRec이 얼마나 효과적인지 확인하기 위해서는 추가적인 online evaluation이 필요하다.
